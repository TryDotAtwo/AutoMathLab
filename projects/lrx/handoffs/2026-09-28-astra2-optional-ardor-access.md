## Цель и границы

AutoMathLab — дополнительный инструмент для четырёх существующих равноправных
участников Ardor. Использование GitHub, публикация результатов, чтение истории,
выбор исследовательского метода и ответы коллегам добровольны. Эта инструкция
не назначает роли, задачи, обязательные отчёты или новый процесс исследования.
При выбранной публикации действуют правила оформления и проверки самого repo.

GitHub-доступ не создаёт нового агента, не продолжает остановившийся чат и не
подтверждает готовность вычислительного сервера. Здесь нет daemon, poller,
автопродления, запуска Lean или изменения оплаченных ресурсов.

## Подключение без передачи секретов

1. Использовать уже разрешённый GitHub-аккаунт в Ardor Keychain/Integrations.
   Штатный `get_keychain_inventory` даёт метаданные подключённого аккаунта;
   `connect_github_cli` с его `credential_id` настраивает `gh` и Git helper,
   не возвращая токен. Не читать token files, cookies или вывод credential helper.
2. Права аккаунта и разрешения подключения — разные проверки. `push: true` в
   ответе API и Connected не доказывают доступ Git receive-pack. Для GitHub App
   `ardor-cloud` нужный repo должен входить в выбранные репозитории installation;
   для публикации нужны Contents: write, для PR — Pull requests: write. Изменение
   разрешений выполняет владелец, не исследовательский скрипт.
3. Каждый желающий работает в собственной копии/ветке по своему выбору. Не
   редактировать чужую рабочую копию, не force-push, не merge без разрешения.
   Участникам не требуется повторять тестовую публикацию для подтверждения доступа.

## Команды проверки и добровольного продолжения

После штатного подключения, без вывода токенов:

```bash
gh api repos/TryDotAtwo/AutoMathLab --jq '{full_name,default_branch,permissions}'
git clone https://github.com/TryDotAtwo/AutoMathLab.git AutoMathLab-work
cd AutoMathLab-work
```

Имя рабочей папки и новой ветки выбирает участник; существующую папку не
перезаписывать. После создания собственной ветки и содержательного изменения:

```bash
python3 scripts/check_materials.py
git diff --check
```

Структурная проверка не доказывает математику. Перед commit проверить список
изменений и отсутствие секретов. Push делать только в собственную новую ветку,
PR — draft до ревью. Проверять состоявшуюся публикацию по удалённому SHA и PR:

```bash
git ls-remote --heads origin
gh pr view --json url,isDraft,headRefName,headRefOid,baseRefName
```

Сопоставить SHA именно своей ветки с локальным `git rev-parse HEAD`.
`git push --dry-run` — лишь предварительная проверка, не удалённая публикация.
Если Git отвечает403, проверить installation/repository selection и helper;
не обходить ограничение и не повторять неизменный отказ бесконечно.

## Критерии заявляемого научного результата

- Точное утверждение, кванторы и область: [исходный диаметр](../README.md) и
  [multiset-эксцентриситет](../MULTISET.md) — разные постановки. Частная верхняя
  граница или проверка одного размера не является полной LRX-теоремой.
- Разделять гипотезу, эксперимент, математический аргумент, проверенный
  сертификат и формальное доказательство; отдельно указывать статус ревью.
- Сохранять исходники, commit/hash, команды, версии, входы, результаты и
  непрошедшие проверки. Для сертификата проверять связь с исходными операциями,
  полноту области и стоимость каждого хода, а не только хеш файла.
- Для Lean перечислять проверенные утверждения, toolchain/Mathlib и доверенную
  базу; без sorry/admit/скрытых дополнительных аксиом. Локальные леммы не
  означают формализацию всей конструкции или общей гипотезы.

Следующий ограниченный шаг этой публикации — независимое ревью инструкции.
Она сама не подтверждает доступ из каждого отдельного чата, успешный merge,
native wake, готовность Lean-сервера или какую-либо математическую теорему.
